MitiruEngine ができるまで

C++ でゲームを作り始め、後輩に教える経験を経て、自作ゲームエンジンの開発に至るまでの記録です。機能はMitiruEngine の紹介ページと紹介サイトにまとめています。

出発点

ゲームを自分で作りたいと考え、会津大学へ進学しました。

三兄弟の末っ子として、兄たちの代から集まった多くのゲーム機と数百本のソフトに囲まれて育ちました。ゲームボーイからドリームキャスト、PlayStation 4 まで、さまざまな年代や種類のゲームを遊びました。

高校では、ノベルゲーム『グリザイアの果実』の松嶋みちるというキャラクターに強く心を動かされました。ゲームを遊ぶだけでなく、自分でも作りたいと考え始めたのはこの頃です。

現在も PC-98DA、Windows XP の実機、ゲーミング PC を使い、古い作品から新しい作品まで遊んでいます。

C++ で完成まで取り組む

大学ではゲーム制作サークルに入り、1 年生の夏に C++ ライブラリの Siv3D を使って初めてゲームを制作しました。ドット絵、シナリオ、ステージに加え、マップを読み込んで表示するプログラムを担当しました。

2 年生の夏には、2 人のチームで初めてリーダーを務めました。設計から細部まで相談しながら実装し、ゲームを完成させました。

当時はスマートポインタを知らず、生ポインタを多用して解放処理も書いていませんでした。大きなメモリリークがあり、学園祭当日までプレイ中にクラッシュする不具合も残っていました。それでも、設計から完成まで一通り経験したことは、その後の開発に役立ちました。

後輩が取り組みやすい設計へ

3 年生でゲーム制作部の部長になり、C++ での開発をどう説明するか、制作の途中でつまずく新入生をどう減らすかを考えるようになりました。

部内では、長く使われてきた Siv3D から Unity へ移る人が増えていました。Unity の GUI は初心者にも理解しやすい一方、C++ でゲームを作れる後輩も育てたいと考えていました。

そこで 3 年生の夏、継承を中心としていた部のコードに、Unity 風のコンポーネント指向を導入しました。「動く」「攻撃する」といった処理を大きな親クラスから分け、プレイヤーや敵が個別の部品として持つ構成です。

変更後は、各自が小さな部品の中に集中して実装できるようになりました。この経験から、一度に確認しなければならない情報を減らすことが、理解しやすさにつながると学びました。

MitiruEngine の開発

ゲームだけでなく、その下で動く仕組みや開発環境にも関心を持ち、『DirectX 12 の魔導書』を読み始めました。ChatGPT に質問しながらサンプルを動かし、グラフィック API を直接使って三角形を表示しました。

3 年生の秋にゲームエンジンの開発を開始しました。設計に詰まるたびに AI と議論し、起こり得る失敗を確認したうえで、自分で方針を決めて試作を重ねました。大学院へ進学した春に、求めていた形へ到達しました。現在も毎週どこかを修正しています。

「Mitiru」という名前は、高校時代に心を動かされた松嶋みちるから取りました。

設計で重視したこと

MitiruEngine では、煩雑な GUI を置かないことを最初から重視しました。

Unity を使った開発では、コードに問題がなくても、インスペクタ上の設定が原因で意図しない動作になることがありました。また、GUI には作業中に必要としない情報も表示されます。

そのため MitiruEngine は全部入りのエディタを持ちません。各機能は 1 ウィンドウとし、通常は何も開かず、コマンドから操作します。ゲームの動作を決める情報はコードとデータに置きます。

特に実現したかった機能は、ホットリロードとゲームの巻き戻しです。コードを保存すると実行中のゲームへ反映し、不具合が起きた時点まで時間を戻して確認できる仕組みを目指しました。

そのため、ゲームの状態をポインタや仮想関数を含まない 1 個のまとまりである flat POD として保持しています。状態をバイト列として扱うことで、コードを差し替えた後も状態を維持できます。毎フレーム保存すれば巻き戻し、入力と一緒に記録すればプレイの再生、ファイルに書けばセーブデータとして利用できます。録画再生、セーブ、観測も同じ仕組みで扱います。

現在の取り組み

現在は MitiruEngine を使い、以前制作したノベルゲームの移植と、新しいゲームの制作を進めています。

ゲームを作ることで不足している機能を見つけ、ゲームエンジンを修正した後に再び制作へ戻る、という作業を続けています。MitiruEngine も、その上で作るゲームも、まだ開発の途中です。
