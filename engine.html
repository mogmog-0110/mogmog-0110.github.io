MitiruEngine

なぜ自分でエンジンを書くのか

Unity / Godot / Unreal / Siv3D はゲームを作るだけなら困りません。それでも書くのは、ゲームが画面に出るまでに何がどう動くかを、使う側でなく書く側から知っておきたいからです。

目的はエンジンそのものではなく、ゲームを深く作れる人間でいるための足場。ゲーム制作は並行して進め、そこで詰まった課題をエンジンへ書き戻しています。

アーキテクチャ

レイヤースタックは以下のとおりです。Native（Mode A）と Hybrid（Mode B）は同じ C++ ランタイムを共有していて、Hybrid はその上に CEF と JS ランタイムが乗ります。

+----------------------------------------------------------+
|  CEF / WEB RUNTIME  (Mode B only)                        |
|  web/mitiru_runtime/*.js  -- mitiru.audio / .save / ...  |
|  HTML / CSS / JS gameplay loaded by CefStartUrl          |
+----------------------------------------------------------+
|  CEF HOST + JS BRIDGES  (Mode B only)                    |
|  mitiru::cef::*  -- MitiruCefContext, AudioBridge, ...   |
+----------------------------------------------------------+
|  APPLICATION LAYER     User Games (Game subclass)        |
+----------------------------------------------------------+
|  ENGINE / SCENE / ECS  Engine, Clock, GameLoop, Screen,  |
|                        SceneManager, GameWorld           |
+----------------------------------------------------------+
|  SUBSYSTEM   Input, Audio, Physics, Network, Render,     |
|              Resource, Asset, Data, Control, Observe     |
+----------------------------------------------------------+
|  PLATFORM    Win32Window | GlfwWindow | Sdl2Window       |
|              | EmscriptenWindow                          |
+----------------------------------------------------------+
|  GRAPHICS    IDevice 抽象の裏で                          |
|              DX11 | DX12 | Vulkan | OpenGL | WebGL | Null|
+----------------------------------------------------------+

GPU バックエンドは全部 IDevice という同じインターフェイスの裏に隠してあります。GPU が無い CI 環境では NullDevice に自動で落とすので、テストはそのまま緑で回ります。

設計の方針

Unity / Godot のような全部入りエディタは作りません。GUI エディタを持たず CLI を中心に据え、機能ごとに独立した小さなツール / ウィンドウへ分けて、必要なときだけ起動する構成にしています。

レイヤーの役割分担も明確です。gameplay・物理・描画は C++、HUD / メニュー / 演出は CEF（HTML/CSS/JS）、純データは JSON。bridge は signal-only で、状態の所有は常に C++ 側に置きます。

差別化の 5 軸

1. HTML/CSS で UI が書ける C++ エンジン

gameplay は C++、UI は CEF 上の HTML/CSS/JS。Web の表現力で HUD やメニューを組みつつ、ゲームの状態は C++ が持つ。両者は signal だけでやり取りします。

2. 決定論 + 自動リプレイ（replay-as-test）

入力を InputSnapshot として記録し、ヘッドレスで bit-exact に再生。実際のプレイ記録を、そのまま回帰テストとして回せます。

3. タイムトラベル・インスペクタ

ゲーム状態を単一の GameMemory に集約する構造保証（ADR-0005）により、過去フレームへの巻き戻しと観察が成立します。

4. 全サブシステムの単独起動

audio / input / render などを単体プロセスで起動して検証できます。エンジン全体を立ち上げずに、関心のある一点だけを触れます。

5. モジュラー・サブウィンドウ

inspector / コマンドパレット / time-travel scrubber などは、ゲーム本体とは独立した別ウィンドウに（ADR-0004）。gameplay 画面とデバッグ系を混在させません。

Host–Game 境界は C-ABI signal-flow（ADR-0005）

ゲームは DLL として配布され、ホストとの境界は POD の C-ABI だけ。ゲームは Engine* を持たず、ホストが状態を POD で push、ゲームは「intent」で要求を返します。境界に std::string や C++ オブジェクトのポインタを渡さないこの規律が、上の決定論・リプレイ・タイムトラベルを構造的に成立させています。ABI は version 番号で管理し、後方互換を保ったまま拡張します。

MitiruEngine で動いているもの

エンジン単体ではなく、実際にゲームに使えている状態かどうかが重要なので、現時点で MitiruEngine 上で動いているプロジェクトを並べておきます。

  • ハトを育てよう（リメイク） — 2023 年に TyranoScript で書いた原作を、MitiruEngine CEF Hybrid + mitiru.novel VM で完全移植。バックログ・既読管理・セーブロードなどの追加要素も入った状態で動いています。
  • かえるクレープへようこそ — 当初は Godot で書いていましたが、現在 MitiruEngine の WASM ビルドへ移植中（1.0.0-rc1）。Playwright による E2E テスト、テーマトークン、itch.io 向けパッケージングまでセットアップ済み。

エンジンを書く作業と、エンジンでゲームを作る作業を、両方を行き来しながら進めています。
