MitiruEngine

ひとりで書き続けている、自作の C++ ゲームエンジンです。ゲームの中身（動き・当たり判定・物理）は C++ で、画面（HUD・メニュー）は Web と同じ HTML / CSS で書きます。2D も GPU 3D（影・MSAA 付き）も描き、書いたコードは止めずにその場で反映、プレイはまるごと巻き戻して観察できます。以下、実機の録画と図解で。

開発中 (v0.31)C++20Windows独自ライセンス（使用自由 / 改変・再配布不可）

これは何か

1 つのゲームを、得意な道具で分けて書く

ゲームは「動くルール」と「見せる画面」でできています。MitiruEngine はそれを別々の言葉で書きます。ルールは速くて壊れにくい C++、画面はレイアウトが得意な HTML / CSS。データ（セリフや設定）は JSON。境界はうすく、状態の持ち主は常に C++ 側です。

下は実際にこのエンジンで作った小さなゲームです。プレイヤーを左右に動かし、落ちてくる星をキャッチしてスコアを伸ばします。プレイヤーや星は C++ が描き、スコアの表示は HTML / CSS です。

2,600+自動テスト
1,000+コミット
2D + 3D同じエンジンで描画
5 秒巻き戻せる開発ツール

描画は DirectX 12 を主軸に、DirectX 11 フォールバックを備えます。バックエンドは内部で IDevice として抽象化していて OpenGL / Vulkan / WebGL / WebGPU の実装も持ちますが、ゲームを通して安定して描けるのは現状 DirectX 12 / 11 です。

ゲームの書き方

状態の struct と、update / draw だけ

書くのは「状態のまとまり（struct）」と「毎フレームの処理（update / draw）」。エンジンは毎フレーム入力を読んで update を呼び、続けて draw で画面を描く。これを 1 秒に 60 回くり返します。最後の 1 行でエンジンに繋がります。 

// 状態は「数値だけ」を struct に持つ
struct StarCatch {
    float playerX = 600;
    int   score   = 0;

    void update(Input in, Hud hud, float dt) {
        if (in.down(Key::Left))  playerX -= 480 * dt;   // ← キーで左へ
        if (in.down(Key::Right)) playerX += 480 * dt;
        hud.set("view.hud.score", score);               // スコアを画面へ送る
    }
    void draw(Screen& s) { /* プレイヤーや星を描く */ }
};
MITIRU_GAME(StarCatch)   // この 1 行でエンジンに繋がる

画面は HTML / CSS で

UI を Web ページのように書く

HUD やメニューは scene.html に HTML / CSS で書きます。C++ が送った値は <span data-m-text="view.hud.score"> のように属性で受けるだけです。つなぎの JavaScript は書きません。やり取りは「信号」だけで、状態の持ち主は C++ のまま。見た目（CSS）とルール（C++）が混ざりません。

止めずに直す（ホットリロード）

数字を変えて、手触りをその場で確かめる

ゲームのコードを保存すると、動いているゲームを止めずにその場で反映されます。プレイヤーの速度・落下のはやさ・背景色を書き換えると、走ったまま変わり、スコアなどの状態はそのまま保たれます。「ちょっと速すぎる / 遅すぎる」を、止めて・直して・また立ち上げる、を待たずに詰められます。

巻き戻して、観察する

過去のどの瞬間にも戻れる

プレイ中の状態は毎フレーム自動で記録されています。開発ツールの時間軸ウィンドウ（ゲームとは別の窓）で値の履歴がグラフになり、グラフの過去をクリックすると、ゲームがその瞬間の状態へまるごと巻き戻ります。「なぜか HP が減った」を、その手前まで戻って目で確かめられます。

同じ仕組みで、走らせたまま観察窓を開けば、playerX や score といった状態をライブで覗けます。さらに、プレイ中の入力はすべて記録されているので、同じプレイをあとからそっくり再生できます。「たまにしか出ないバグ」を録画して何度でも再現する、テストとして毎回流す、といった使い方ができます。

なぜ巻き戻しや録画リプレイが、こんなに素直にできるのでしょうか。その秘密は、ゲームの状態を「ポインタも std::vector も持たない、丸ごとコピーできる 1 個の構造体」（flat POD）に置く、という設計の約束にあります。次のセクションで、その原理を。

状態を 1 個の flat POD に置く

巻き戻し・録画・観察が成り立つ、たった 1 つの約束

前のセクションの「巻き戻し」「録画リプレイ」「ライブ観察」は、別々に作った機能ではありません。すべて 1 つの約束から生まれています。ゲームの状態を flat POD（Plain Old Data）にまとめておくこと、それだけです。

flat POD とは、ざっくり言えば「ポインタも可変長コンテナも持たない、固定サイズの数値のかたまり」です。int / float と固定長配列だけで作った struct です。std::string や std::vector、ヒープへのポインタは入れません。すると、その状態はメモリ上で 1 本の連続したバイト列になります。ここがすべての鍵です。

連続したバイト列であることが効いてきます。状態が「あちこちのヒープに散らばったオブジェクトをポインタで辿る」形だと、全体を保存するには参照を 1 つずつ追って深いコピーが要ります。でも flat POD なら、こうなります。

  • 保存 ＝ そのバイト列を memcpy で 1 回コピーするだけ
  • 差分 ＝ memcmp でフレーム間の変化が取れる
  • 巻き戻し ＝ 過去のバイト列を現在へ memcpy で書き戻すだけ
  • JSON 化（観察） ＝ フィールドのオフセットを読むだけ

つまり「状態をまるごと扱う」が、特別な仕掛けではなくただのバイト操作になります。だから巻き戻しも録画も観察も、別々ではなく同じ 1 つの土台の上に乗ります。

動き方はこうです。MITIRU_GAME(struct) はコンパイル時に「その struct が本当に flat POD か」を static_assert で検査します（違反するとビルドが通りません）。実行中、ホストは毎フレーム状態のバイト列をリングバッファに記録。巻き戻しは過去のバイト列を書き戻すだけ。録画リプレイは「ある時点のスナップショット＋それ以降の入力（これも記録済み）」を流し直すと、決定論的に同じ結果が bit 単位で再現されます。観察は MITIRU_REFLECT でフィールドを名前付きの JSON にして覗きます。

副作用として、構造的にキャッシュに優しい

flat POD の縛りには、決定性とは別の御利益が付いてきます。キャッシュ効率です。状態が連続したバイト列だと、

  • ポインタ追跡が消える。データキャッシュミスの最大の原因は、参照を辿ってヒープのあちこちへ飛ぶこと。この構造体はそれをしません
  • 毎フレームのヒープ確保がゼロ。FixedVec はインライン領域なので、確保のヒッチも断片化も出ません
  • 小さな状態が常駐する。数 KB の状態を毎フレーム舐めるので、キャッシュにホットなまま居座ります（時間的・空間的局所性）

ただし flat POD が保証するのは「連続」までで、自動で最適ではありません。FixedVec<Enemy, N> のような配列の構造体（AoS）だと、敵 1 体の座標だけ舐めたくても構造体まるごとがラインに乗ります。大量エンティティのホットループを本気で詰めるなら、次の一手は SoA（構造体の配列）です。座標は座標、HP は HP を別々の連続配列に分け、SIMD とプリフェッチが 100% 効く形にします。Unity DOTS / Unreal Mass のような ECS や、data-oriented design が突き詰めている領域です。

代償は「トップの struct に std::string / std::vector / ポインタ / 画像を直接持てない」こと。長さの要る所は固定長の FixedString / FixedVec を使い、画像などはグローバル／別オブジェクトに分けます。この縛りこそが、上の力を生みます。

これが差別化の核です。 状態が数千のオブジェクトに散らばったエンジンでは、「全状態をまるごと読む／戻す」が原理的に作れません。最初から状態を 1 個の flat POD に縛ったからこそ、巻き戻し・録画リプレイ・AI 観測が同じ仕組みで成立します。

2D も、GPU 3D も

正面は 2D + HTML/CSS ですが、3D も同じ書き方で出せます。draw の中で s.camera3D でカメラを決め、s.drawMesh でメッシュ（立方体・球・板・読み込んだモデル）を置くだけ。あとはエンジンの GPU 3D レンダラーが、影（シャドウマップ）とアンチエイリアス（MSAA）付きで描きます。文字（HUD）は 2D でその上に重なります。

もちろん 2D も同じエンジン・同じ書き方です。下はブロック崩しで、ボールやブロックの動きは C++、上部のスコア・残機・レベルの表示は HTML / CSS です。

大量ポリゴンや凝ったシェーダーを前提にした本格 3D は対象外です。あくまで「2D に 3D を混ぜる」「小〜中規模の 3D を出す」ための道具です。

実際に、ゲームを出せる

エンジンは「実際にゲームを出せる道具」になっていてこそです。このエンジンの上で動いている作品を並べておきます。

  • オスカーのガーデニング。まいたリズムを次の小節で返すタイミングゲーム。ゲームの全状態を 1 個の構造体に閉じ込めてあるので、下で説明した巻き戻し・録画リプレイ・観察がそのまま効きます
  • ハトを育てよう（リメイク）。2023 年に作ったノベルゲームを、このエンジン上で完全移植。セーブ・ロードやバックログなどの追加要素込みで動いています
  • かえるくれーぷ（Kaeru Crepe）。UI をすべて HTML / CSS で組んだクッキング × ノベル。調理の中核を実機で遊べる形まで仕上げ済み
  • FLUID DROP。積んだブロックがゼリーや液体に変わる落ちものパズル。EA SEED の流体シミュレーション（PB-MPM）を DirectX 12 へ移植して仕込んでいます
  • 同梱の章立てサンプル。巻き戻し（rewind）・観察（observe）・HTML/CSS の UI などを、1 機能ずつ実機で触れる機能のショーケース

向いていること・いないこと

目的はエンジンそのものではなく、ゲームを深く作れる人間でいるための足場です。Unity / Godot のような全部入りエディタは作らず、逆に振っています。道具は 1 つにつき 1 ウィンドウ、ふだんは何も開かない、操作はコマンドから。エディタは Visual Studio でも VS Code でもメモ帳でも構いません。

  • 向いている。2D + HTML/CSS UI のゲーム／巻き戻し・録画リプレイ・観察が効く決定論的なゲーム／2D に 3D を混ぜる
  • 向いていない。大量ポリゴンや凝ったシェーダー前提の本格 3D。そこは別のエンジンの方が向いています
